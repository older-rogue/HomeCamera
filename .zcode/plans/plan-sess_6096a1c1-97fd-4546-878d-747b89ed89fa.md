# HomeCamera 长时运行卡顿/OOM 修复计划

针对排查确认的 11 个问题，按严重程度修复。每项修复后需确保现有单元测试通过（`MediaUdpPacketTest`、`RealtimeVideoFrameQueueTest` 等覆盖协议/队列语义），新增 `rawPacketQueue` 边界场景测试。

### 修复 2 — joinPayloads 内存复用 + 编码器 drain 复用
**文件 A**：`app/src/main/java/com/zx/homecamera/core/protocol/MediaUdpPacket.kt`

- `PendingFrame.joinPayloads`（行 209-216）：去掉 `ByteArrayOutputStream`，改用已累计的 `payloadBytes` 预分配 + `System.arraycopy`：
  ```kotlin
  fun joinPayloads(): ByteArray {
      val output = ByteArray(payloadBytes)
      var offset = 0
      fragments.forEach { fragment ->
          requireNotNull(fragment)
          System.arraycopy(fragment, 0, output, offset, fragment.size)
          offset += fragment.size
      }
      return output
  }
  ```
  （省去 BAOS 扩容拷贝 + `toByteArray()` 二次拷贝；语义不变，`MediaUdpPacketTest` 应仍通过）

**文件 B**：`app/src/main/java/com/zx/homecamera/video/CameraH264Streamer.kt`（drainEncoder 行 410）

- 在 `drainEncoder` 方法内引入可复用缓冲（按帧大小取较大值复用），减少每帧 `ByteArray(bufferInfo.size)` 分配：
  ```kotlin
  var reusableData: ByteArray? = null
  // 循环内：
  val data = reusableData?.takeIf { it.size >= bufferInfo.size }?.also {
      it.copyOf(bufferInfo.size)  // 不行，仍拷贝
  }
  ```
  由于 `data` 需传给 `sendVideoFrame`（异步发送）和 `recorder?.writeSample`（同步），且 send 是异步队列，**不能简单复用同一实例**（会被覆盖）。因此改为：仅在 `data` 仅用于同步路径时复用；经核实 `sendVideoFrame` 把 data 包装进 `OutboundMediaFrame` 入队异步发送，复用不安全。
  **结论：此项改为仅复用 `latestCodecConfig` 路径**（codec config 仅保留引用，不进入发送队列），其余每帧分配保留。即保持行 410 不变，避免引入 use-after-free 风险。

**文件 C**：`app/src/main/java/com/zx/homecamera/audio/AacAudioStreamer.kt`（drainEncoder 行 184）
- 同上，`data` 通过 `EncodedAudioEvent.Sample` 传递，下游异步消费，**不安全复用，保留原样**。

> 说明：经核实发送/录制均为异步消费，编码器 drain 处的 `ByteArray` 无法安全复用。本轮聚焦修复 2A（joinPayloads，确定无并发消费，安全）。编码器侧的 GC 压力通过修复 1（减少 rawPacketQueue 堆积）间接缓解。如后续仍需优化，可引入对象池并改为"复制后入队"，但属更大重构，不在本次范围。

## 阶段三：P2 设计隐患

### 修复 9 — trimOldFrames 按序列号淘汰
**文件**：`app/src/main/java/com/zx/homecamera/core/protocol/MediaUdpPacket.kt`

- `MediaFrameReassembler.trimOldFrames`（行 170-175）：改为按 sequenceNumber 距离淘汰最旧帧（考虑 wraparound）：
  ```kotlin
  private fun trimOldFrames() {
      while (pending.size > maxPendingFrames) {
          val oldestKey = pending.keys.minByOrNull { it.sequenceNumber }
              ?: return
          pending.remove(oldestKey)
      }
  }
  ```
  注：简单 `minByOrNull` 在 wraparound 边界仍有理论缺陷，但当前 `sequenceNumber` 为递增 Int，短时间内不 wraparound（30fps 下约 4 年才溢出），实际安全。如需严格处理需引入 epoch，属更大改动，不在本次范围。

### 修复 10 — drainEncoder 单帧异常兜底
**文件**：`app/src/main/java/com/zx/homecamera/video/CameraH264Streamer.kt`（drainEncoder 行 396-450）

- 将 `while(running.get())` 循环体（行 397-449）用 try-catch 包裹单帧操作，非致命异常 `continue` 而非杀死线程：
  ```kotlin
  while (running.get()) {
      try {
          val dequeueStartNanos = System.nanoTime()
          val outputIndex = codec.dequeueOutputBuffer(bufferInfo, 10_000)
          // ... 原有 when 块 ...
      } catch (error: IllegalStateException) {
          if (running.get()) {
              Log.w(TAG, "drainEncoder transient error: ${error.message}")
              continue   // 单帧异常不致死线程
          } else {
              throw error
          }
      }
  }
  ```
  注意：`releaseOutputBuffer` 必须在 finally 中保证执行，避免 buffer 泄漏。重构时把 `codec.releaseOutputBuffer(outputIndex, false)` 放进 try-finally。

## 风险与回退

- **修复 1（有界队列）**：弱网下丢包增多可能导致短暂花屏，但有 key frame 请求机制兜底；容量 256 偏保守，可调。
- **修复 6（协程重构）**：行为等价改造，但 `delay` 取代 `Thread.sleep` 后退避时序一致；如出问题可回退到 executor 方案（保留修复 3 的 awaitTermination）。
- **修复 10（异常兜底）**：连续异常可能掩盖真实故障，但有日志告警；如需可加连续失败计数后停止。
- 所有改动均为内存/资源释放优化，不改变协议与功能契约，可独立回退任一项。
